# 参考 PM-NAUTILUS 的可靠性与性能优化

日期：2026-10-16。PM-F 基线为 `413aa0d05bcb18a50f56bf06cfcd10f84a89bf2f`；
只读参考 PM-NAUTILUS 的 `c83d79c24430c53d49a991a6dcf0056b612f248a`。

## 适用范围

PM-F 是 TypeScript 跟单系统；PM-NAUTILUS 是 Python/NautilusTrader 策略系统。
此次采用后者在完整数据、交易归属、异步状态和重复计算方面的处理思路，保留 PM-F
原有跟单金额、买卖筛选、风险设置、数据库结构及 `PAPER + LIVE_DISABLED` 启动方式。
没有复制后者的扫描策略、目标价算法或钱包托管方式，也没有修改 PM-NAUTILUS。

## 具体改动

| 部分 | 原问题 | 当前行为 |
| --- | --- | --- |
| 仓位分页 | 达到分页上限时，部分仓位可能被当作完整账户用于对账 | 必须读到完整末页，否则返回 `POSITIONS_PAGE_SATURATED`；Live 只读钱包按既有错误路径显示不可用 |
| Observe 缓存 | 新成交的仓位或余额刷新失败后，事件头已提前标记完成，下一次可能复用旧账户缓存 | 完整对账刷新成功后才提交事件头；失败后即使仍在缓存 TTL 内也会重试 |
| 订单归属 | 关联订单号的成交未充分核对市场、资产和方向 | 提交、查询、待确认成交和恢复均校验身份；恢复还对照持久化本地意图，错回报不写账、不释放预留资金 |
| maker 成交 | 顶层 taker 的资产不一定是本程序 maker 的资产 | 按角色核对 maker 自身资产，兼容互补 token 和 SDK 可缺省的 maker side |
| 订单恢复 | 状态与成交分别读取，两次之间确认进度变化可能形成旧状态配新成交 | CLOB 状态和成交共用一次已校验快照；其他适配器保留原接口兼容 |
| 网页异步状态 | 已发出的旧轮询可能覆盖操作成功后的新状态或制造过期连接错误 | 操作、钱包失效和退出推进请求版本，过期回复不再更新页面；防止重复提交，安全退出可优先执行 |
| HTTP 超时 | 获取响应头后即撤销计时，慢 JSON 响应体可能一直卡住轮询 | 轮询超时覆盖整个响应体读取 |
| 深盘口撮合 | 对每个二分候选反复复制、汇总全部已成交档位 | 累积已确认的金额和原始费用，完整可吃档位直接通过，仅最后部分档位需要二分；保留原整数舍入和预算边界 |
| 桌面脚本运行时 | 脚本前置其他 Node 安装路径，可能在同一验证中改变版本和兼容性哈希 | 保留调用者选择的工具链，仅追加 Finder 所需的安装目录；回归验证其他宿主 Node 不会抢占 |
| 持续验证 | 仓库没有 GitHub 自动验证 | push、PR 和手动触发均在 macOS 15 执行锁定依赖安装、类型检查、全套测试、浏览器脚本及启动器语法检查 |

新文件纳入现有构建身份及隔离测试文件清单；Live 运行时哈希仍覆盖全部源码和测试。
源码改变后，应重新生成相应验证证据，不能用旧工件证明新版本具备实盘就绪状态。

## 验证

本地环境：macOS arm64、Node.js `24.19.0`（满足项目 Node 24 约束）、pnpm `11.9.0`。
CI 从 `.node-version` 读取 `24.14.0`，从 `package.json` 读取 pnpm 固定版本。
使用 macOS runner 是因为现有桌面生命周期测试依赖 BSD `script` 和 zsh；本次没有声称完成 Linux 桌面适配。
时间显示测试使用当前时区的期望值，同时排除旧目标时间；无需改变产品时区。
耗时的打包集成测试按其现有子进程超时设置测试期限，保留全部验证断言。

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
for script in prototype/live-ui/*.js prototype/live-ui/*.mjs; do
  node --check "$script"
done
zsh -n scripts/launch-hecatonchires-ui.command
git diff --check
```

原版本：77 个测试文件、939 项测试通过；当前版本：79 个测试文件、997 项测试全部通过。
锁定依赖安装、TypeScript 检查、全部浏览器脚本、启动器语法及 `git diff --check` 均通过。
新增回归覆盖分页边界、刷新失败重试、错市场/资产/方向、合法 maker 成交、恢复期间的
快照一致性、网页请求乱序、钱包连接和失效、退出抢占、慢响应体、撮合预算/舍入及脚本运行时选择。

撮合额外对比了 2,001 组新旧实现输入，逐项输出一致。单机 400 档盘口、每个实现运行
3 次的合成测量，中位耗时从约 `343.3 ms` 降至 `0.51 ms`。这是纯撮合函数诊断，
结果受输入与机器影响，不代表网络、签名、交易所响应或真实成交速度。

## 验证边界

此次只操作源码和隔离测试，没有连接真实钱包、读取私有账户、启动 Live、发送订单、
写链或更新任何服务器。没有复制历史账本或旧验证工件；源码克隆不包含
`validate:live-production` 需要的历史 Paper 报告，因此本次未生成新的生产验收工件。
自动检查通过也不能替代真实成交、费用、持仓及赎回闭环验收。

PM-NAUTILUS 的现金计量 BUY 与 PM-F 的既有 size-bound BUY 模型不同。本轮保留后者的
份额上限和状态语义；更优价格下的完整订单语义需要独立核对签名数量、实际回报、
预算与恢复兼容性，不能只放宽一次成交校验。本次改动不构成该项实盘语义已经验收的证明。
